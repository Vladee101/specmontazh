# Спецификация модуля ТО слаботочных систем

Oct 23, 2026 · @Vlad

Редакция 2.0: спецификация приведена к ТЗ заказчика MVP 1.2 от 24.10.2026. При расхождении приоритет у ТЗ; схема БД проверена тестами на PostgreSQL 16.

## 1. Назначение и границы

Модуль ведёт один рабочий цикл: объект → регламент → плановое задание → выполнение инженером → приёмка руководителем. Обслуживаются четыре типа систем: пожарная сигнализация, СОУЭ, охранная сигнализация, видеонаблюдение. Заказчик ТЗ — ООО НПО «Спецмонтаж»; проект некоммерческий, развёртывается на собственном VPS.

**В объёме MVP 1.2:** три роли; объекты, системы, оборудование; четыре готовых чек-листа; регламенты; создание заданий за 5 дней; назначение, перенос, отмена; доработка и приёмка; фильтры и история задания; табличный отчёт и CSV. Это 18 сценариев (UC 01–15, 19, 20, 21) и 13 User Story (US-01–08, 10, 12–15).

**Вне объёма:**

- отдельный процесс устранения неисправностей (замечание — это текст к проверке);
- цепочка замен оборудования; справочник заказчиков (заказчик — строка `customer_name`);
- конструктор чек-листов и версии шаблонов; шаблоны правит руководитель в своём разделе интерфейса;
- графики, аналитика и полный аудит карточек;
- US-09, US-11 (отложены) и UC-16, 17, 18, 22 (исключены);
- восстановление из архива и перенос системы между объектами.

**Источники и приоритет.** ТЗ MVP 1.2 (PDF/DOCX), `User_Stories_MVP.md`, `model_mvp.json`, `ERD_MVP.mmd`. Если этот документ расходится с ТЗ, права у ТЗ.

## 2. Роли и права

Бизнес-роль администратора не даёт доступа к объектам, ТО и шаблонам. Шаблоны чек-листов правит руководитель в своём разделе интерфейса (API `/templates`), администратору они недоступны (AT-02).

| Роль | Может | Не может |
| --- | --- | --- |
| Администратор (`admin`) | Создавать и менять пользователей, назначать роли, блокировать и активировать, сбрасывать пароль | Объекты, системы, оборудование, регламенты, шаблоны, задания, отчёт |
| Руководитель (`manager`) | Объекты, системы, оборудование, регламенты; шаблоны чек-листов; назначение, перенос, отмена, приёмка, возврат; список заданий, отчёт, CSV | Управлять пользователями |
| Инженер (`engineer`) | Видеть и выполнять только свои задания: начало, результаты, замечания, отправка | Чужие задания (ответ `403`), справочники на запись, приёмка |

Сервер проверяет роль, назначение и состояние записи при каждой операции. Блокировка пользователя завершает его сессии. Нельзя убрать или заблокировать последнего активного администратора. Смена роли инженера с незавершёнными назначениями запрещена до передачи заданий.

## 3. Статусы, просрочка и бизнес-правила

Задание проходит семь статусов; переходы допускаются только через команды из таблицы, произвольный `PATCH status` запрещён. После приёмки или отмены результаты не редактируются.

| Из | Действие | В | Кто |
| --- | --- | --- | --- |
| Создано (`created`) | Назначить инженера | Назначено (`assigned`) | Руководитель |
| Назначено | Начать ТО | В работе (`in_progress`) | Инженер |
| В работе, На доработке (`rework`) | Отправить результат | На проверке (`in_review`) | Инженер |
| На проверке | Принять полный результат | Принято (`accepted`) | Руководитель |
| На проверке | Вернуть с комментарием | На доработке | Руководитель |
| Любой, кроме Принято и Отменено | Отменить с причиной | Отменено (`cancelled`) | Руководитель |

**Просрочка вычисляется, не хранится.** Она есть у заданий в статусах Создано, Назначено, В работе и На доработке после окончания `current_due_date` (календарный день Europe/Moscow). «На проверке» показывается отдельно, Принято и Отменено в текущие просрочки не входят. Историческое нарушение `has_deadline_violation` не стирается переносом срока: перенос до окончания срока нарушения не создаёт, а перенос уже просроченного задания факт сохраняет.

**Замена инженера** статус не меняет: «Назначено» ставится только при первом назначении. Для задания «На проверке» сначала нужен возврат.

| Код | Правило |
| --- | --- |
| BR-01 | Задание создаётся за 5 календарных дней до срока. Если регламент подключён позже, задание создаётся сразу; исторические задания не создаются. |
| BR-02 | После сбоя пропущенные сроки восстанавливаются без дублей. На паузе задания не копятся; при возобновлении руководитель задаёт ближайшую дату. |
| BR-03 | Перенос — только с причиной. Исходный срок сохраняется, график следующих ТО не сдвигается. |
| BR-04 | Частичный результат можно отправить, принять частичное ТО нельзя. «Не применимо» требует обоснования. |
| BR-05 | Неисправность — замечание к проведённой проверке; не блокирует приёмку полного ТО и не создаёт процесс ремонта. |
| BR-06 | Отмена — для непринятого задания, с причиной. Отмена не выполнение и не вызывает повторную генерацию. |
| BR-07 | Название оборудования читается из карточки (в том числе в старом задании); текст и обязательность проверок копируются в задание. |
| BR-08 | Запись с историей не удаляется. Оборудование выводится из эксплуатации; объекты и системы архивируются после завершения или отмены открытых заданий. |
| BR-09 | История обязательна для статусов, исполнителей и сроков. Общий аудит справочников не ведётся. |
| BR-10 | Отчёт и CSV строятся по одной выборке исходных плановых дат; отменённые показываются отдельно от выполненных. |

## 5. Планировщик

Генерация — отдельная команда приложения, а не HTTP-эндпоинт. Запуск: ежедневно в 00:10 по Europe/Moscow (таймер systemd) и сразу после активации регламента (та же функция вызывается из API). Часовой пояс, время и горизонт в 5 дней — в конфигурации. События хранятся в UTC, сроки — типом `date`.

Алгоритм для каждого регламента со статусом `active`:

1. Начать транзакцию и заблокировать строку регламента (`SELECT … FOR UPDATE`). Проверить, что регламент, система и объект активны.
2. Пока `next_due_date` не позже «сегодня по Москве + 5 дней», обрабатывать её по очереди. Так после сбоя восстанавливаются все пропущенные сроки действующего периода.
3. Проверить пару (`regulation_id`, `original_due_date`). Если задание уже есть, в том числе отменённое, дубль не создаётся.
4. Собрать фактический чек-лист: активное оборудование системы и применимые пункты шаблона (по всей системе либо по `equipment_type_filter`). Если список пуст, это ошибка настройки: транзакция откатывается, срок не продвигается, ошибка пишется в технический журнал.
5. Создать задание в статусе `created`, строки `task_equipment`, копии пунктов в `task_check` (текст и обязательность фиксируются), первую запись истории статусов.
6. Продвинуть `next_due_date` по исходному графику и перейти к следующему сроку. Фиксация — одна транзакция на регламент.

**Месяцы считаются от опорной даты** `schedule_anchor_date`: 31 января → 28 (29) февраля → 31 марта. Перенос задания опорную дату не меняет. При возобновлении после паузы руководитель задаёт новую ближайшую дату, опорная дата сбрасывается на неё, период паузы не восполняется.

**Защита от дублей двойная:** блокировка строки регламента и уникальный индекс (`regulation_id`, `original_due_date`). Остаточный риск: если руководитель сменит график регламента, новые даты могут совпасть с уже созданными заданиями. Ключ задан ТЗ, поэтому принят как есть.

## 6. Результаты проверок, отправка и приёмка

У каждого пункта `task_check` результат пуст, пока инженер его не заполнил. Допустимые значения: `passed` (норма), `deviation` (замечание), `not_applicable`, `not_checked`.

| Событие | Правило |
| --- | --- |
| Сохранение результата | Для `deviation`, `not_applicable` и `not_checked` комментарий обязателен (не пуст после удаления пробелов). Автор и время сохраняются вместе с результатом. |
| Черновик | Сохраняется явной кнопкой, статус не меняется. |
| Отправка (`submit`) | Пустой обязательный пункт блокирует отправку. Обязательный `not_checked` отправку допускает. Нужна фактическая дата: не в будущем и не раньше создания задания. Сервер сам считает `is_partial`. |
| Приёмка (`accept`) | Только из «На проверке». Сервер заново проверяет: обязательные пункты заполнены и нет обязательного `not_checked`. Частичное ТО принять нельзя. |
| Возврат (`return`) | Комментарий обязателен. Статус «На доработке», инженер редактирует тот же результат, каждая повторная отправка пишется в историю. |
| Замечание о дефекте | Это комментарий к проведённой проверке (`deviation`). Не блокирует приёмку полного ТО, отдельной карточки ремонта нет. |

После отправки инженер результаты не меняет, после приёмки или отмены их не меняет никто. Смена статуса и запись истории выполняются в одной транзакции; при приёмке, переносе, назначении и отмене сервер заново проверяет актуальную версию записи (`version`), конфликт даёт `409`.

## 7. Модель данных

PostgreSQL 16, 13 таблиц из `model_mvp.json` и служебная `sessions`. Источник истины — `schema.sql`; 131 тест в `schema_test.sql` проходит на PostgreSQL 16.15. Идентификаторы — `bigint generated always as identity`, события — `timestamptz`, сроки — `date`, значения-перечисления — `text` с `CHECK`. К полям ТЗ добавлены только `version` (оптимистичная блокировка), последовательность номеров заданий и представление отчёта `v_task_report`.

| Таблица | Назначение | Главные ограничения в БД |
| --- | --- | --- |
| `users` | Учётные записи, роль | Уникальный `lower(login)`; роль из трёх значений |
| `service_object` | Объект и заказчик строкой | Название, заказчик, адрес не пусты; архив = флаг и дата вместе |
| `low_current_system` | Одна из четырёх систем объекта | Тип из четырёх; тип не меняется при оборудовании, регламентах, заданиях |
| `equipment` | Устройство | Вывод требует даты и причины; не раньше установки |
| `checklist_template` | Шаблон на тип системы | `system_type` уникален |
| `template_item` | Пункт шаблона | Позиция уникальна в шаблоне; фильтр типов только у пунктов по оборудованию, непустой массив |
| `maintenance_regulation` | Периодичность и график | Период > 0, единица `month`; тип шаблона = тип системы; активация требует активного шаблона с пунктами и неархивных системы и объекта |
| `maintenance_task` | Задание | Уникальны `task_number` и (`regulation_id`, `original_due_date`); система совпадает с системой регламента; статус согласован с полями; переходы только по таблице раздела 3; исходный срок и номер не меняются |
| `task_equipment` | Состав оборудования | Пара уникальна; оборудование из системы задания |
| `task_check` | Копия пункта и результат | Элемент оборудования только из того же задания; комментарий обязателен для всех результатов, кроме `passed`; результат, автор и время заполняются вместе |
| `task_deadline_change` | Переносы | Только добавление; новая дата отличается; причина не пуста |
| `task_assignment_history` | Назначения | Только добавление; новый инженер задан и отличается от прежнего |
| `task_status_history` | Статусы и отправки | Только добавление; первая запись — `created`; для возврата и отмены обязателен комментарий |
| `sessions` | Сессии (вне ERD заказчика) | Хеш токена, CSRF-токен, `ON DELETE CASCADE` по пользователю |

**Связи.** Объект → системы → оборудование; шаблон → пункты; система и шаблон → регламент → задания; задание → состав оборудования, проверки и три истории. Заказчик — строка в объекте. Удаление не каскадируется, кроме пунктов шаблона и сессий: запись с историей удалить нельзя (BR-08).

**Остаётся за приложением** (в БД не выразимо или зависит от текущего времени): фактическая дата не в будущем и не раньше создания задания; первая дата регламента не в прошлом; блокировка архивации и вывода из эксплуатации при открытых заданиях; запрет смены роли инженера с незавершёнными заданиями и удаления последнего администратора; проверка набора `equipment_type`; активность назначаемого инженера; автоматическая приостановка регламентов при архивации.

**Просрочка в БД не хранится.** Представление `v_task_report` считает `is_overdue` по московскому дню и `has_deadline_violation`: просрочено сейчас, срок переносили после его истечения, либо работа выполнена позже действующего срока. Определение второго признака ТЗ не задаёт; оно подтверждено заказчиком (раздел 13).

## 8. Отчёт и CSV

Таблица и CSV строятся одной выборкой по исходным плановым датам с фильтрами: объект, тип системы, текущий исполнитель, статус. Перенос не уводит задание из исходного периода; отменённые попадают в выборку, пока их не отфильтровали, и не считаются выполненными. Частичный результат виден со своим статусом.

Формат: UTF-8 с BOM, разделитель `;`, даты `YYYY-MM-DD`, одна строка на задание, экранирование штатным сериализатором, защита текстовых полей от формул (значения, начинающиеся с `=`, `+`, `-`, `@`). Пустой период даёт файл с одной строкой заголовков.

| Столбец | Содержимое |
| --- | --- |
| `task_number` | Номер задания |
| `object_name`, `customer_name`, `address` | Актуальные сведения об объекте |
| `system_name`, `system_type` | Название и тип системы |
| `engineer_name`, `status` | Текущий исполнитель (пусто, если не назначен) и статус |
| `original_due_date`, `current_due_date` | Исходный и действующий сроки |
| `actual_performed_on`, `accepted_at` | Фактическая дата и время приёмки (могут быть пусты) |
| `is_overdue`, `has_deadline_violation` | Текущая просрочка и историческое нарушение |
| `is_partial` | Результат представлен частично |
| `remarks` | Непустые комментарии проверок с названиями проверки и устройства плюс общий комментарий инженера |
| `review_comment`, `cancellation_reason` | Комментарий руководителя и причина отмены |

## 9. API

Префикс `/api/v1`. Одно действие — один обработчик; проверки доступа и статусов общие. Ошибки: `401` нет входа, `403` нет прав, `404` запись отсутствует или недоступна, `400` неверные поля, `409` конфликт состояния. Тело ошибки: `code`, `message`, `field_errors`. Чужое задание у инженера — `403`, как в ТЗ (проверка AT-01).

| Ресурс или команда | Операция | Доступ |
| --- | --- | --- |

| `/users`, `/users/{id}` | GET, POST, PATCH | Администратор |
| `/users/{id}/block`, `/users/{id}/activate` | POST | Администратор |

| `/engineers` | GET: инженеры для назначения и фильтров | Руководитель |
| `/objects`, `/systems`, `/equipment` | GET, POST; PATCH карточки | Руководитель; инженер читает свои |
| `/objects/{id}`, `/systems/{id}`, `/equipment/{id}` | DELETE пустой карточки | Руководитель |
| `/objects/{id}/archive`, `/systems/{id}/archive` | POST | Руководитель |
| `/equipment/{id}/decommission` | POST с датой и причиной | Руководитель |

| `/regulations/{id}/pause`, `/resume` | POST; при возобновлении задаётся `next_due_date` | Руководитель |
| `/templates`, `/templates/{id}` | GET; PATCH названия и `is_active` | Руководитель |
| `/templates/{id}/items`, `/templates/{id}/items/{item_id}` | POST, PATCH, DELETE пункта | Руководитель |

Команды изменения принимают текущую `version` записи; несовпадение даёт `409`. Нет API заказчиков, дефектов и замен. Ограничения полей (предложение ТЗ): логин 3–150 символов, названия до 255, адрес до 500, телефон до 32; пароль 8–128 символов (принятое умолчание).

**Команды, которые требуют пояснений.**

| Команда | Тело | Правила |
| --- | --- | --- |
| `POST /users/{id}/password` | `password`, `version` | Сохраняется только хеш. Все сессии пользователя удаляются в той же транзакции, включая собственную сессию администратора, если он сбрасывает пароль себе. |
| `GET /engineers` | `?include_inactive=true` | Ответ: `id`, `full_name`, `is_active`, число незавершённых заданий. По умолчанию только активные: назначить можно только их (UC 12). Заблокированные нужны в фильтре списка заданий и отчёта. Не открывает руководителю `/users`: логинов и ролей в ответе нет. |
| `POST /regulations/{id}/activate` | `version` | Только из `draft`. Приложение проверяет, что `next_due_date` не в прошлом; триггер БД проверяет активный непустой шаблон того же типа и неархивные систему и объект. Генерация (раздел 5) идёт в той же транзакции: если для ближайшего срока чек-лист пуст, активация откатывается с `409` и кодом `empty_checklist`. Ответ — регламент и созданные задания. |
| `PATCH /templates/{id}` | `name`, `is_active`, `version` | Создания и удаления шаблонов нет: по одному на тип системы, создаются командой seed. Нельзя сделать неактивным шаблон, по которому есть активные регламенты (`409`). |
| `POST`, `PATCH`, `DELETE /templates/{id}/items…` | `section_name`, `check_text`, `target_type`, `equipment_type_filter`, `is_required` | Новый пункт встаёт в конец. Правка и удаление не затрагивают выданные задания: в `task_check` хранится копия, ссылка на пункт при удалении обнуляется (AT-22). Нельзя удалить последний пункт шаблона с активными регламентами (`409`). |
| `PUT /templates/{id}/items/order` | `item_ids` (все пункты шаблона) | Список должен совпадать с набором пунктов шаблона, иначе `400`. Позиции переписываются в одной транзакции; уникальность (`template_id`, `position`) не отложенная, поэтому сначала позиции сдвигаются за пределы текущих, затем ставятся `1..N`. |
| `PUT /tasks/{id}/checks` | `version`, `checks: [{ id, result, comment }]`, `engineer_comment` | Только в «В работе» и «На доработке», только назначенный инженер. Все пункты сохраняются в одной транзакции: ошибка в одном отклоняет весь запрос, `field_errors` с путями вида `checks[3].comment`. Пункты не из этого задания дают `400`. Автор и время записываются только у изменённых пунктов. Ответ — новая `version` задания. |
| `POST /tasks/{id}/submit` | `version`, `actual_performed_on`, `engineer_comment` | `engineer_comment` необязателен; если передан, перезаписывает сохранённый в черновике. Он попадает в столбец `remarks` отчёта. |

## 10. Нефункциональные требования и поставка

| Область | Требование |
| --- | --- |
| Безопасность | Сервер заново проверяет роль, назначение и состояние при каждой операции. Пароли — хеш `scrypt` (`node:crypto`) с солью. Сессии: HttpOnly, Secure при HTTPS, SameSite=Lax, CSRF-токен, простой 8 часов; блокировка и сброс пароля удаляют сессии. Ограничение частоты входа. Пароли и секреты не попадают в логи. |
| Целостность | Команды заданий и генерация транзакционны; блокировка строки регламента и уникальные индексы против дублей; `version` против потери чужих правок. |
| Время | Часовой пояс Europe/Moscow, запуск генерации в 00:10, горизонт 5 дней — в конфигурации. События в UTC, сроки как `date`. |
| Производительность | Стенд: 100 объектов, 5 000 устройств, 10 000 заданий. Списки с пагинацией и карточки открываются до 2 секунд. Настройки и результат замера — в README. |
| Планировщик | Команда приложения вне пользовательских запросов (таймер systemd). Ошибки генерации пишутся в технический журнал (journald). |
| Интерфейс | Форма инженера работает на ширине 360 пикселей. Списки с фильтрами и пагинацией. Черновик сохраняется явной кнопкой. |
| Развёртывание | Без платных сервисов. Общий VPS: nginx как обратный прокси, HTTPS через certbot (Let's Encrypt), API как служба systemd, зафиксированные версии зависимостей. |

**Передаётся:** исходный код, зафиксированные зависимости, SQL-миграции и демонстрационные данные; четыре шаблона для согласования и команда их первоначального заполнения; инструкция запуска, настройки планировщика и создания первого администратора; описание прав руководителя в административной части; тесты критичных правил и результаты AT-01–AT-22; инструкция резервного копирования с проверенным восстановлением (`pg_dump`); краткие инструкции руководителя и инженера; описание CSV.

**Готовность MVP:** реализованы 18 сценариев, пройдены все приёмочные проверки, частичное ТО не принимается, дублей нет, CSV корректен, доступ проверяется сервером.

## 11. Стек и архитектура

ТЗ предлагает Python и Django, но называет это техническим предложением: обязательны серверная логика и критерии приёмки. Выбран один язык на всё приложение и схема БД как источник истины.

| Слой | Решение | Зачем |
| --- | --- | --- |
| Язык | TypeScript | Один язык для API, интерфейса и общих типов |
| API | Fastify, валидация zod | Лёгкий сервер, схемы запросов совпадают с типами |
| Интерфейс | React + Vite (SPA) | Форма инженера на 360 px, списки с фильтрами |
| Доступ к БД | Kysely, SQL-миграции | SQL-first: схема правит код, а не наоборот |
| БД | PostgreSQL 16 | Ограничения, триггеры, блокировки строк |
| Пароли и сессии | `scrypt` из `node:crypto`, таблица `sessions`, cookie HttpOnly | Без внешних зависимостей; блокировка сразу завершает сессии |
| Планировщик | Команда приложения по таймеру systemd | Вне HTTP, часовой пояс в таймере, ошибки в журнал |
| Тесты | Vitest + `schema_test.sql` | Правила БД и сценарии AT |
| Развёртывание | nginx + certbot, systemd | VPS уже обслуживает другие проекты через nginx; без платных сервисов |
| Резервные копии | `pg_dump` + проверенное восстановление | Требование поставки |

**Цена выбора.** В Django административная часть для шаблонов идёт из коробки. В Fastify её нет: нужны экран правки шаблонов для руководителя (раздел шаблонов в интерфейсе руководителя, без конструктора) и команда первоначального заполнения четырёх шаблонов (seed).

## 13. Принятые умолчания и открытые вопросы

ТЗ эти места не определяет. Умолчания приняты на время разработки и подлежат подтверждению заказчиком.

| Вопрос | Принято | Кому |
| --- | --- | --- |
| Набор значений `equipment_type` | В БД непустой текст; набор проверяет приложение, начальный список приходит от заказчика | Заказчик |
| Содержание четырёх шаблонов | Заполняется организацией перед внедрением; в проекте тестовые пункты | Заказчик |
| Статусы регламента | `draft`, `active`, `paused` | Подтвердить |
| Единицы периода | Только `month` | Подтвердить |
| Формат номера задания | `ТО-000123`, из последовательности | Подтвердить |
| Пропущенные сроки после сбоя | Создаются все, без дублей | Подтвердить |
| Замена инженера | Статус не меняется, `assigned` только при первом назначении | Подтвердить |
| Опорная дата при возобновлении | Сбрасывается на заданную ближайшую дату | Подтвердить |
| Сброс пароля | Администратор задаёт новый пароль в карточке пользователя | Подтвердить |
| `has_deadline_violation` | Просрочено сейчас, либо срок переносили после истечения, либо выполнено позже срока; перенос до срока делает руководитель с записью в историю, нарушением не считается | Подтверждено заказчиком |
| Смена графика регламента | Новые даты могут совпасть с уже созданными заданиями; ключ из ТЗ дубль не даст, расписание не перестраивается | Принято |
