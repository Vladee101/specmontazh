# Модуль контроля ТО слаботочных систем

Веб-модуль для планирования, выполнения и приёмки технического обслуживания (ТО) слаботочных систем: пожарная сигнализация, СОУЭ, охранная сигнализация, видеонаблюдение.

Заказчик: ООО НПО «Спецмонтаж». Проект выполняется как дипломная работа, некоммерческий. Требования: ТЗ «MVP 1.2 от 24.10.2026» (оно главнее любых более ранних черновиков).

> **Статус.** Реализованы API, планировщик и интерфейс по макетам для всех трёх ролей; 55 тестов Vitest и 131 тест схемы проходят. Развёрнуто на https://specmontazh.online, восстановление из резервной копии проверено. Инструкции пользователей — в `docs/instructions/`.

## Что делает система

- Хранит объекты, их системы и оборудование.
- По регламентам (периодичность в месяцах) автоматически создаёт задания на ТО за 5 дней до плановой даты.
- Инженер заполняет чек-лист, указывает фактическую дату и отправляет результат на проверку.
- Руководитель назначает исполнителей, переносит сроки, возвращает на доработку, отменяет и принимает ТО.
- Отчёт за период с выгрузкой в CSV.
- Администратор управляет пользователями.

Границы MVP: 18 сценариев использования (UC 01–15, 19, 20, 21), 3 роли, 7 статусов задания, 4 типа систем. Что в MVP не входит, перечислено в спецификации (раздел 1).

## Роли

| Роль | Основное |
|---|---|
| `admin` | Пользователи: создание, правка, блокировка, сброс пароля |
| `manager` | Объекты, системы, оборудование, регламенты, шаблоны, задания, приёмка, отчёт |
| `engineer` | Свои задания: чек-лист, отправка на проверку |

Статусы задания: `created`, `assigned`, `in_progress`, `in_review`, `rework`, `accepted`, `cancelled`. Просрочка не хранится, а вычисляется по текущему сроку.

## Принцип: схема БД — источник истины

Целостность держится на уровне PostgreSQL, а не только в коде:

- составные внешние ключи (задание ↔ регламент и система, проверка ↔ оборудование задания);
- триггеры: счётчик версий, неизменяемые поля задания, допустимые переходы статусов, append-only истории, соответствие типа шаблона типу системы, запрет смены типа системы;
- CHECK-ограничения, связывающие статус с обязательными полями;
- уникальность `(regulation_id, original_due_date)`, включая отменённые, исключает дубли при повторном запуске планировщика;
- представление `v_task_report` — единый источник для таблицы отчёта и CSV.

В приложении остаются только правила, зависящие от текущего времени: фактическая дата не в будущем, первая дата не в прошлом, запрет архивирования при открытых заданиях, запрет смены роли инженера с открытыми заданиями. Полный перечень — в спецификации, раздел 7.

Если запрос не проходит схему, исправляется запрос, а не схема.

## Планировщик

Запускается раз в сутки в 00:10 по Europe/Moscow командой приложения `node apps/api/dist/scheduler.js`. Запуск делает таймер `deploy/systemd/sm-to-scheduler.timer`. Время сервера UTC, поэтому часовой пояс указан в самом таймере (`OnCalendar=… Europe/Moscow`). `Persistent=true` выполняет пропущенный запуск после перезагрузки. Журнал запусков:

```bash
journalctl -u sm-to-scheduler
```

Та же функция генерации вызывается из API сразу после активации и возобновления регламента, в той же транзакции: если чек-лист пуст, активация откатывается. Ошибка одного регламента не мешает остальным; при ошибках команда завершается с кодом 1, и systemd отмечает запуск как неудачный. Заодно удаляются сессии, простой которых превысил 8 часов.

Ручной запуск на сервере (например, после восстановления из копии):

```bash
systemctl start sm-to-scheduler && journalctl -u sm-to-scheduler -n 20
```

Алгоритм: для каждого активного регламента найти плановые даты, попадающие в окно 5 дней вперёд, и создать недостающие задания с копией пунктов шаблона и списка оборудования. Повторный запуск безопасен: дубли отсекаются уникальным ключом в БД. Месяцы считаются от опорной даты: 31 января → 28 февраля → 31 марта. Приостановленные регламенты пропускаются, пропущенные за паузу задания не восполняются.

## Локальный запуск

Требования: Node.js 22 или новее, PostgreSQL 16 (подойдёт и более новый).

```bash
npm install
```

Файл `.env` в корне (в git не попадает):

```ini
NODE_ENV=development
DATABASE_URL=postgresql://postgres@localhost:5432/sm_to_dev
TZ=Europe/Moscow
ADMIN_LOGIN=admin
ADMIN_PASSWORD=admin-pass-1
DEMO_PASSWORD=demo-pass-1
```

```bash
createdb sm_to_dev
npm run db:migrate
npm run db:seed -- --demo   # 4 шаблона, администратор и демо-данные
npm run dev                 # API :3010, интерфейс http://127.0.0.1:5173
```

Демо-данные: руководитель `m.petrov`, инженеры `a.sokolov` и `d.orlov` (пароль из `DEMO_PASSWORD`), четыре объекта из макетов, действующие регламенты и задания на ближайшие дни. Без `--demo` создаются только шаблоны и администратор. В разработке Vite проксирует `/api` на API, поэтому интерфейс и API работают на одном origin, как за nginx.

Генерация заданий вручную: `npm run scheduler --workspace apps/api`.

Переменные окружения (`.env.example`):

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | строка подключения к PostgreSQL (на сервере — unix-сокет, без пароля) |
| `HOST`, `PORT` | адрес API: `127.0.0.1:3010` |
| `APP_ORIGIN` | origin фронтенда для проверки `Origin` (CSRF); CORS не нужен, SPA и API на одном домене |
| `TZ` | `Europe/Moscow` |
| `SCHEDULER_HORIZON_DAYS` | горизонт генерации, 5 |
| `ADMIN_LOGIN`, `ADMIN_PASSWORD`, `ADMIN_FULL_NAME` | первый администратор при начальном наполнении; после него удалить |
| `DEMO_PASSWORD` | пароль демо-пользователей для `seed --demo`; на рабочем сервере не нужен |
| `SESSION_IDLE_HOURS`, `LOGIN_RATE_LIMIT`, `TRUST_PROXY`, `LOG_LEVEL` | необязательные: простой сессии (8), попыток входа в минуту (10), адрес прокси (127.0.0.1), уровень журнала (info) |

Секреты в репозиторий не попадают. Отдельный секрет подписи cookie не нужен: токен сессии случайный, в БД хранится его хеш.

## Развёртывание на VPS

Сервер общий с другими проектами: Ubuntu 24.04, nginx на 80/443, PostgreSQL 16 и Node 22 уже установлены, Docker нет. Проект встраивается рядом, ничего общего не меняя: своя БД и роль в общем PostgreSQL, свой системный пользователь, API на `127.0.0.1:3010`, свой сайт в nginx. Системный часовой пояс (UTC) не трогаем.

Все команды выполняются от root по SSH. Развёртывание идёт в два этапа: подготовка сервера не зависит от кода приложения, её можно сделать заранее.

### Этап 1. Подготовка сервера (до появления кода)

С рабочего компьютера скопировать папку `deploy` на сервер (PowerShell, из папки проекта):

```bash
scp -r deploy root@91.229.91.234:/root/sm-to-deploy
```

На сервере:

```bash
# 2 ГБ swap: при 2 ГБ памяти сборка может не поместиться
fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab

# пользователь, БД и роль; вход в PostgreSQL по peer, без пароля
useradd --system --home /opt/sm-to --shell /usr/sbin/nologin smto
sudo -u postgres createuser smto
sudo -u postgres createdb -O smto sm_to
mkdir -p /var/backups/sm-to && chown smto:smto /var/backups/sm-to && chmod 700 /var/backups/sm-to

# временная страница, пока нет сборки фронтенда
mkdir -p /opt/sm-to/apps/web/dist
echo '<!doctype html><meta charset="utf-8"><title>Спецмонтаж</title><p>Модуль ТО: идёт подготовка.</p>' > /opt/sm-to/apps/web/dist/index.html

# сайт nginx
cp /root/sm-to-deploy/nginx/proxy-headers.conf /etc/nginx/snippets/sm-to-proxy.conf
cp /root/sm-to-deploy/nginx/sm-to.bootstrap.conf /etc/nginx/sites-available/sm-to
ln -s /etc/nginx/sites-available/sm-to /etc/nginx/sites-enabled/sm-to
nginx -t && systemctl reload nginx

# HTTPS: certbot допишет блоки 443 в /etc/nginx/sites-available/sm-to
certbot --nginx --redirect -d specmontazh.online -d www.specmontazh.online
```

`nginx -t` перед перезагрузкой обязателен: ошибка в конфиге уронит все сайты сервера. Если `nginx -t` сообщил об ошибке, `reload` не выполнится (из-за `&&`), и остальные сайты продолжат работать на старом конфиге.

`sm-to.bootstrap.conf` нужен только для первого выпуска сертификата. После certbot итоговый конфиг с HTTPS хранится в `deploy/nginx/sm-to.conf` (копия с сервера). Дальнейшие правки сайта делаются в нём и копируются на сервер поверх `/etc/nginx/sites-available/sm-to`, снова через `nginx -t && systemctl reload nginx`. Копировать на сервер с сертификатом `sm-to.bootstrap.conf` нельзя: он сотрёт настройки HTTPS.

Сертификат продлевает таймер certbot, который уже есть на сервере. Проверка продления: `certbot renew --dry-run`.

### Этап 2. Установка приложения

```bash
# временная страница больше не нужна, папка должна быть пустой для git clone
rm -rf /opt/sm-to

# код
git clone https://github.com/Vladee101/specmontazh.git /opt/sm-to && chown -R smto:smto /opt/sm-to
cd /opt/sm-to && cp .env.example .env && chmod 600 .env && chown smto:smto .env
nano .env

# сборка и миграции от имени smto; --env-file передаёт настройки из .env
sudo -u smto npm ci
sudo -u smto npm run build
sudo -u smto node --env-file=.env apps/api/dist/migrate.js
sudo -u smto node --env-file=.env apps/api/dist/seed.js     # 4 шаблона и первый администратор
nano .env                                                    # удалить ADMIN_PASSWORD

# службы
cp deploy/systemd/sm-to-* /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now sm-to-api sm-to-scheduler.timer sm-to-backup.timer
```

В `sm-to-api.service` путь `/usr/bin/node`; проверить его командой `command -v node`. Проверка после запуска:

```bash
systemctl status sm-to-api --no-pager && curl -s https://specmontazh.online/api/health
```

Обновление:

```bash
cd /opt/sm-to && sudo -u smto git pull && sudo -u smto npm ci && sudo -u smto npm run build
sudo -u smto node --env-file=.env apps/api/dist/migrate.js && systemctl restart sm-to-api
```

Логи API: `journalctl -u sm-to-api -f`.

### Резервные копии

`sm-to-backup.timer` в 03:30 МСК запускает `deploy/backup.sh`: `pg_dump -Fc` в `/var/backups/sm-to`, хранение 14 дней. Копия на том же сервере не защищает от потери сервера, поэтому её нужно периодически забирать к себе:

```bash
scp root@<IP>:/var/backups/sm-to/*.dump .
```

Проверка восстановления (до сдачи работы, не после): `deploy/restore-check.sh <файл.dump>` разворачивает копию во временную БД, выводит число строк в основных таблицах и удаляет временную БД.

## API

Префикс `/api/v1`. Единый формат ошибок: HTTP-код (400, 401, 403, 404, 409, 429) и тело `{ code, message, field_errors }`, при необходимости `details` (например, список заданий, блокирующих архив). Таблица методов — в спецификации, раздел 9. Проверка работоспособности: `GET /api/health`.

Изменяющие запросы требуют заголовок `X-CSRF-Token` (значение приходит в ответе `/auth/login` и `/auth/me`) и принимают текущую `version` записи.

## Отчёт и CSV

Отбор по исходной плановой дате (перенос срока не переводит задание в другой период). CSV: UTF-8 с BOM, разделитель `;`, даты `YYYY-MM-DD`, 18 фиксированных столбцов с русскими заголовками (`CSV_COLUMNS` в `apps/api/src/services/report.ts`), статус и тип системы — названиями, признаки — «Да»/«Нет», значения с `=`, `+`, `-`, `@` в начале экранируются от формул. Отменённые задания выводятся отдельно и выполненными не считаются.

## Нефункциональные требования

До 100 объектов, 5000 устройств, 10000 заданий; ответ на типичные запросы и отчёт — не более 2 секунд. Фиксируется замером на тестовом наборе данных, а не оценкой.

## Открытые вопросы

Подробный список — в спецификации, раздел 13. Главные:

1. Список типов оборудования (`equipment_type`) должен прислать заказчик; пока это начальный список по макетам в `apps/api/src/lib/labels.ts`.
2. Определение «нарушение срока» в `v_task_report` — предложение, нужно подтверждение заказчика: просрочено сейчас, срок перенесён после истечения прежнего, либо фактическая дата позже текущего срока.
3. Содержание пунктов шаблонов — пример, реальные проверки согласует организация.
